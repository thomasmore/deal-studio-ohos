Concrete implementation plan

01 / Exact scope

Six concrete changes.
Not a new agent framework.

Recommended first patch: use the existing whole-screen writer to write a multi-screen app as one shared contribution.

Let the plan name screens

NeedsPlan.ets

02 / Actual blockers in the current code

“Use ui.Screen” alone will not work.

Three existing assumptions discard or prohibit the application structure.

Parser

Screen metadata is ignored

NeedsPlan.ets / parseNeedsPlan()
keep = [title, eyebrow, subtitle, inputs, constants, questions]

A model can return screens, but the parser currently has nowhere to keep them.

Planning bridge

The app becomes one list

NeedsPlan.ets / sketchFrom()
first entries → Sketch.list second entries → other

Medicines and dose records cannot both remain structured collections through this representation.

Writer contract

Multiple views are discouraged

AgentCustom.ets / CONTRACT
“add ONE section” “no second view … of entries”

The prompt treats a second presentation as duplication, even when it belongs on a different screen.

The language can already compile named screen functions. The restrictions above are in the agent.02 / 10

03 / Change 1 — planner and parser

Keep needs once. Reference them from screens.

Modify NeedsPlan.ets: NEEDS_PROMPT, Need, NeedsPlan and parseNeedsPlan().

// Proposed JSON shape; existing need details omitted.
{
  "needs": [
    {"id":"medicines", "type":"entries", …},
    {"id":"todayDoses", "type":"other",
     "uses":["medicines"], …},
    {"id":"medicineEditor", "type":"other",
     "uses":["medicines"], …}
  ],
  "screens": [
    {"id":"today", "needs":["todayDoses"]},
    {"id":"medicines", "needs":["medicines"]},
    {"id":"editMedicine", "needs":["medicineEditor"]}
  ],
  "startScreen":"today",
  "transitions":[
    {"from":"medicines", "to":"editMedicine",
     "on":"add or edit", "record":"medicines.id"}
  ]
}

Concrete changes

  • Stable IDs for all needs, including entries.
  • Optional screen definitions and transitions.
  • References such as uses mean shared data, not a copied collection.
  • Validate IDs and references locally.
Compatibility: an old plan without screens still means one main view and uses the old path.
No second model call to plan screens. These are additions to the existing planning reply.03 / 10

04 / Change 2 — preserve the plan

Make the handoff before flattening.

NeedsChoose.composeNeeds() must recognize a multi-screen plan before entering single-screen implementation choices.

NowNeedsChoose.ets → VeraCompose.ets
drawPlan() → sketchFrom(plan) → buildChooseRequest() → composeFromSketch()

drawPlan() currently requires a usable Sketch. The caller then proceeds using its one list, one clock and ordered sections.

Adding screens only to the JSON cannot preserve them through this chain.

First patchComposeResult.appPlan — proposed field
parse and validate the plan → ordinary one-screen plan: old path → multi-screen plan: carry appPlan directly to the shared writer

Update drawPlan()/drawOnce() to accept and preview an app plan without requiring the lossy Sketch.

Keep questions, cancellation and unasked-need filtering. Do not rewrite Sketch into a generic multi-collection composer yet.

The existing single-screen composer remains unchanged for its supported requests.04 / 10

05 / Change 3 — orchestration

Reuse the whole-screen hole, deliberately.

In VeraAgent.runAgent(), handle appPlan before building the old single-screen parts.

1. Prepare one planBuild ScreenPlan directly from app needs—not the flattened Sketch.
→
2. Call writeHole()Existing batched SDK lookups, one related code contribution.
→
3. Assemble + settleExisting composeFragments(), compilation, smoke and bounded repair.
VeraAgent.ets

Branch after planning, not after failure

When appPlan is present, write its related screens together. Do not first spend time composing the same request as one flat screen.

VeraBuildRoute.ets

Do not fall back to a flattened app

If the app write still fails after its repair budget, report that failure. Do not retry through a legacy path that discards its screen structure.

Trade-off of this first cut: multi-screen apps use custom code, rather than maximum catalogue-block reuse.05 / 10

06 / Change 4 — writer contract

The existing reply format is enough.

Add an app-mode contract in AgentCustom.ets. Do not invent a second code language or one reply per screen.

ScreenPlan.ets → AgentHole.ets → CustomRequest

Pass the app context through

Carry its screen IDs, need relationships and transitions into the writer request.

Require predictable names such as c_view_today for declared screen functions.

In app mode, one “section” means one shared code contribution. It may contain several named views.

<fields>
c_screen: string = "today"
c_medicines: C_Medicine[] = []
… shared fields and isolated draft fields …
</fields>
<functions>
function c_view_today(state: AppState): ui.View { … }
function c_view_medicines(state: AppState): ui.View { … }
function c_view_editMedicine(state: AppState): ui.View { … }
… shared handlers; keep __PASSTHROUGH__ …
</functions>
<view>
Choose only the active named view using if/else.
sections.push(active);
</view>
Each named view returns ui.Screen(...). The writer supplies view bodies and navigation behavior; the host supplies the program shell.06 / 10

07 / What does not need rewriting

Leave the fragment compositor alone for now.

The earlier deck suggested a larger assembly change than the first working version needs.

Already supportedVeraTemplates.ets / FragmentSpec
VeraSectionCompose.ets / composeFragments()
  • Shared classes and state fields.
  • One initialization contribution.
  • Arbitrary helper functions—including named view functions.
  • A view block that can call those functions.
  • One generated AppState, init() and AppTheme.
Small integration change

Use the existing shell correctly

Suppress the outer common header with the existing __HEADER_STYLE__ = none. Each active screen can provide its own header.

The custom contribution’s view block dispatches to its named views. Only the active Screen is pushed into the AppTheme.

Deferred: placing separate catalogue blocks into named screens and sharing their data owners through ports.
No new FragmentSpec.views model is required for this first patch. That belongs to the later cross-screen reuse work.07 / 10

08 / Change 5 — exact prompt changes

Replace conflicting instructions.

Not just a paragraph saying “support multiple screens.”

Planning

NeedsPlan.ets / NEEDS_PROMPT

Current assumptionEntries brings its form, list and buttons as one screen structure.

New ruleDefine a record collection once. Screens reference it; editing and listing may be different presentations.

Custom writing

AgentCustom.ets / CONTRACT

Current instruction“ONE section”; “no second view” of existing entries.

App-mode instructionOne shared contribution may define several screens. Avoid duplicate ownership—not legitimate views on different screens.

Save semantics

rawfile/vera-skill.txt

Current instruction“Do not add … a save button.”

ReplacementNo “Save app state” button. A domain Save commits a copied draft; Cancel leaves shared records unchanged.

Also: add stable screen/record IDs, Back and async-state rules. Include the catalogue specs for Screen + BackHandler in app mode, without paying for a discovery call. Apply the same contract to refine and repair.
One short neutral list/editor example is enough. Do not insert PillPal’s product policies into every system prompt.08 / 10

09 / Change 6 — checks and refinement

Check every declared view. Preserve the app.

Extend the existing acceptance step, not a model-review pipeline for each screen.

agent/AgentRepair.ets / checkProgram()
VeraSmoke.ets + host tests

Additional bounded checks

  • Each planned view function exists and compiles.
  • Views handle empty or missing selections without trapping.
  • One active screen under one AppTheme.
  • Targeted fixtures exercise navigation, draft cancel/save and shared records.

Effects are mocked here. This does not prove native API reliability or arbitrary app semantics.

VeraAgent.ets / VeraBuildRoute.ets
existing refine + repair prompts

Prevent unsafe structural edits

Do not attach the old flat composition record to an app when that record cannot represent screen placement.

Use the existing model-refine path instead, preserving state fields and unrelated named views.

Do not let “add a section” silently append UI outside the active Screen. Screen-aware structural editing is later work.
Keep existing repair limits. A failed editor does not justify regenerating every screen or replanning the request.09 / 10

10 / Concrete outcome

What happens for the next PillPal request?

One normal successful app write, with the existing verification and bounded repair—not three generation chains.

MODEL / PLAN

One needs plan

Medicines, doses, screens and transitions.

→
HOST / ROUTE

App-mode handoff

Keep the full plan; do not flatten it into one list.

→
MODEL / CODE

One contribution

Shared fields, handlers and named screen views.

→
HOST / ACCEPT

One module

Assemble, check, then save through the normal project path.

First patch is complete when…

A generated app can add a record, show it on another screen, edit/cancel, go Back and reopen with saved data. Existing simple prompts still use their old path.

Not part of this patch

A generic multi-screen block compositor, automatic screen-by-screen reviews, new persistence APIs, or exactly-once SDK recovery.

This is a concrete proposal, not implemented agent behavior. Runtime support is already in place.10 / 10
